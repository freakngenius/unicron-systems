## What Z17 actually shipped vs what Z17.1 corrects

Z17 already wired in `runZedcorZ17Backfill()` (Wave 5) which loads pre-existing
un-enriched construction rows and runs them through score → GC → pitch →
Notion-gated. **The backlog enrichment worked.** What Z17 got wrong:

1. **Metric naming hid the work.** Wave 5 reported its counts under new
   `backfill_*` fields, while the original `enrichment_attempted` /
   `enrichment_succeeded` (which the orchestrator UI and any monitoring
   reads as the canonical "did this trigger do enrichment work?" signal)
   stayed at 0 on every re-run with no new ingests. The Z17.1 spec
   author saw `enrichment_attempted: 0` on run #6719 and reasonably
   concluded the backlog was untouched — even though #6719 actually ran
   on pre-Z17 code (started 07:55:19Z, before the 07:58:24Z merge), so
   there was no Wave 5 to look at either way.

2. **Cap was too tight for a single-trigger drain.** Wave 5's per-run cap
   defaulted to 30 rows. With ~190 construction rows in the backlog,
   that's 6+ triggers to clear it. Spec acceptance #4 ("trigger twice;
   second run attempts ~0") implicitly demands the first trigger handle
   most of the backlog in one shot.

3. **GC extraction was sequential.** Each GC fetch is ~2s of HTTP work.
   At 177 backlog rows needing GC, sequential extraction is 354s —
   already over the 300s Vercel ceiling before pitch + Notion costs.
